## What this is

**Data-Pipeline** (package `data-pipeline`) reads heterogeneous production data sources — PDFs, XML,
spreadsheets — and turns them into OMC-JSON. It is a **library and CLI, not a service**:
`Labkoat-API` consumes it and runs the pipelines in worker threads.

**`README.md` is the real documentation** — 15 KB covering the layer model, running a pipeline,
writing a new one, library use, the Script-E source in detail, the OMC mapping output and schema
versions. Read it before changing anything here. This file carries only what the README does not:
the cross-repo facts, and the rules.

Generated docs: `npm run jsdoc` → `docs/jsdoc/`. There is also
`docs/scriptE-source-analysis.md`.

## Architecture

Four layers, each usable on its own — the README's own summary, kept here because it is the single
most useful thing to know:

```
src/pipelines/          the uniform way in. A registry of self-describing pipelines, and the
                        context through which they read. Knows no sources and no formats.
src/sources/<source>/   one adapter per supplier. Reads a delivery, emits tables in OMC
                        terminology, and declares its mapping as data. No OMC construction.
src/omc/                generic. Turns tables + declarative mappings into validated OMC
                        entities. Knows no sources.
src/lib/                xml, csv, pdf, tabular, paths. Knows neither.
```

The interim tabular format is the spine, not a side-output: a source produces it and the OMC layer
consumes it. It already uses OMC terminology, so a second source maps into the same shape rather than
into a Script-E-shaped one.

**Three sources exist** — `frameio`, `scriptE`, `yamdu` — registered in `src/pipelines/registry.js`.

**A new source needs a parser that emits tables and a mapping that is data. It needs no OMC code.**
See `src/sources/scriptE/omcMapping.js` for what a mapping looks like.

## Hard rules

**Never restate the OMC schema.** Shapes, edge paths, inverses, identifier prefixes and validation are
all asked of `omc-util` per call, for whichever `schemaVersion` the caller passes. That is what makes
`--schema-version .../v2.8` an option rather than a code change. This package maintains no tables of
entity types, edge keys or cardinality of its own — keep it that way.

**The mappings are the only place this package names OMC properties**, so they are the only thing a
schema change can invalidate. `checkMappings()` runs before any data is read and names every property
and edge the target version does not accept. Do not bypass it.

**A pipeline declares the credentials it needs by name and never learns where they are kept.**
`Labkoat-API/src/pipeline/secrets.js` resolves them. Do not read a secret or an environment variable
from a pipeline.

## Traps

- **This repo has no git remote and no tags.** `Labkoat-API` declares
  `"data-pipeline": "git+https://github.com/MovieLabs/omc-data-pipeline.git#semver:^1.0.0"`, which
  resolves to nothing. **A change here does not reach the Portal until it is linked:**

  ```bash
  npm link                            # here, once per machine
  cd ../Labkoat-API && npm run link:local
  ```

  Any `npm install` in Labkoat-API destroys that link and silently restores a stale copy. **Nothing
  can be deployed until this repo is pushed and tagged** — a Docker build has no working copy to
  link to.
- **`files` in `package.json` governs what ships.** It includes `src` wholesale, so a new source
  directory ships without being added — but a new *top-level* directory does not.
- `types/` is generated by `build:types` and committed; it drifts from source unless regenerated.

## Code style

ESLint flat config (`eslint.config.js`) with the `@stylistic` plugin, matching the rest of the
platform: 4-space indentation, single quotes, semicolons, trailing commas on multiline,
`prefer-const`, `no-var`, `prefer-template`, import ordering builtin → external → internal → parent →
sibling → index (alphabetized), unused vars prefixed `_` allowed.

JSDoc is preferred, and this repo takes it seriously — types are resolved globally from
`src/types.js` and feed the TypeScript build.
